# 設計判断の記録（リードが書く）

1件ずつ: 日付・決めたこと・理由・捨てた案。

- （例）2026-01-01: データ層は SQLite ではなくインメモリにする。理由: 起動の速さが採点に効くため。捨てた案: SQLite（ファイル I/O が遅い）。

- 2026-11-22: main.ts をバイト列変換器にする（本体は transducer.js、solve.js は正しさのアンカーとフォールバックとして残す）。cases.json を JSON.parse せず、各ケースの text を JSON のエスケープ形のまま CSV として走査し、答えの JSON を直接バイトで書く。JSON.stringify が出さない形（`\/`・非正規の `\u`・キーの重複や欠け・text が文字列でない等）はそのケースだけ JSON.parse → runJson、不正な UTF-8 や想定外の構造はファイル全体を元のやり方で解く。一致は scripts/fuzz-main.mjs（main.ts を書き方の変種・負荷ケース・練習の3倍で端から端まで実行）で確認。Docker の bench（10回の中央値）で net 約 91ms（空実行 62ms を引いた値）、旧版 net 約 257ms の 0.354 倍。
  - 本体を .js に分けた理由: .ts は Node が型除去にかけ、本体ほどの大きさだと1回 約 50ms かかる（main.ts の頭で process.exit しても 107ms、1行の import だけなら 55ms、空は 53ms）。
  - 準備走行を入れた理由: 最適化されたコードが未通過の分岐に入るたびに「型情報の不足」で最適化が外れ、練習セットで 18 回・約 60ms をインタプリタでやり直していた。全分岐を通る合成テキストを先に 8 周読む（答えは捨てる）と 0 回になり、走査が約 128ms → 約 68ms。V8 の段階フラグ（invocation-count-for-maglev/turbofan、no-maglev など）は効かなかった。
  - 捨てた案: 4バイト単位の SWAR 走査（位置の揃え方が入力と出力で違い複雑）、ネイティブの indexOf で区切りを探して塊でコピー（フィールドが平均 14 バイトと短く、呼び出しの方が高い）。
- 2026-11-22: 変換器の改善（bench net 約 91ms → 約 79ms、Docker・12回の中央値の交互計測）。
  - header を text の前に探すのをやめた（`,"header":` の Buffer.indexOf が全テキストを舐めていた）。header が無いものとして書き、値が分かってから先頭レコードを columns の位置へ詰め、エラーの row を直す（先頭レコードまで null、後ろは 1 減らす）。詰めた後に空白が入るが、採点は JSON の値で比べるので同じ。
  - 区切りの無い 4 バイトを DataView でまとめて写す（SWAR）。特殊文字の位置は Math.clz32 で求め、1 バイトずつの後始末を省く。
  - `--no-concurrent-recompilation` を実行中に設定（1 CPU では並行コンパイルの方が CPU 時間が多い）。
  - `--no-turbo-loop-peeling` を実行中に設定（TurboFan のコンパイルが軽くなる。net 約 79ms → 約 67ms。他の turbo-* フラグは誤差）。
  - 床（Docker、空実行を引いた net）: 読みだけ 4.8ms、読み＋12MB 書き 14.2ms、読み＋UTF-8 検証＋書き 16.6ms。
